# ADR 07: Экспорт PDF-отчётов через Thymeleaf + openhtmltopdf, синхронная генерация

## Статус
Accepted

## Контекст
Требовался экспорт в PDF: успеваемость и оценки ученика, табель ученика,
табель класса для учителя. Рассматривались варианты генерации:
- **iText 7/8** — отклонён: избыточно сложный/громоздкий API для задачи
  такого масштаба.
- **JasperReports** — отклонён: вёрстка отчётов через отдельные XML-
  шаблоны (`.jrxml`) неудобна в поддержке и медленно итерируется по
  сравнению с обычной вёрсткой.
- **HTML/CSS-шаблон через Thymeleaf + рендер в PDF через openhtmltopdf**
  — выбран: позволяет верстать отчёты как обычные HTML-шаблоны (тот же
  templating engine, что уже используется в стеке), а не осваивать
  специфичный XML-формат отчётного движка.

Известное ограничение `openhtmltopdf` — поддержка CSS не выше CSS 2.1 с
частичной поддержкой CSS3 (без flexbox/grid в актуальной версии на
момент выбора). Это ограничение было заранее известно и учтено при
вёрстке шаблонов.

Кириллица потребовала явного подключения кастомных шрифтов (PT Sans,
Regular/Bold) через `PdfRendererBuilder.useFont(...)`, поскольку
встроенные PDF-шрифты кириллицу не поддерживают; это же решение дало
более аккуратный и единообразный внешний вид отчётов.

## Решение
PDF-отчёты генерируются синхронно, в потоке HTTP-запроса:

1. Контроллер собирает данные отчёта через доменный сервис (например,
   `GradeReportService`).
2. Данные прогоняются через Thymeleaf-шаблон (`templateEngine.process(
   templateName, context)`) → HTML-строка.
3. HTML рендерится в PDF через `openhtmltopdf` (`PdfRendererBuilder`,
   `useFastMode()`, кастомные шрифты PT Sans) в `ByteArrayOutputStream`.
4. Готовые байты PDF отдаются напрямую в `ResponseEntity<byte[]>` с
   `Content-Disposition: attachment`.

Явного пула потоков под рендеринг не выделено — вызов выполняется в том
же потоке, что обслуживает HTTP-запрос (стандартный поток Tomcat).

## Последствия
+ Вёрстка отчётов через привычный HTML/CSS/Thymeleaf, без необходимости
  осваивать специфичный формат отчётного движка.
+ Простая, линейная модель "запрос → данные → HTML → PDF → ответ", без
  дополнительной инфраструктуры (очередей, отдельного хранилища файлов,
  поллинга).
+ Корректное отображение кириллицы и единообразный вид отчётов за счёт
  явного подключения шрифтов.
- Рендеринг PDF (CPU-bound операция) выполняется в общем пуле потоков
  Tomcat — при одновременном массовом запросе отчётов (типичный
  сценарий: конец четверти, когда табели запрашивают многие ученики/
  родители/учителя разом) есть риск, что рендеринг начнёт конкурировать
  за CPU с остальным API сервиса и деградировать его отзывчивость в
  целом, а не только сам экспорт.
- Ограничение CSS 2.1+ у `openhtmltopdf` (без flexbox/grid) сужает
  возможности вёрстки шаблонов — учтено и заложено в текущие шаблоны, но
  требует той же осторожности при добавлении новых отчётов.
- **Запланированное улучшение**: вынести рендеринг в выделенный
  ограниченный (bounded) thread pool через `@Async` с отдельным
  `Executor`, чтобы изолировать CPU-нагрузку PDF-рендеринга от остального
  API без перехода на полноценную асинхронную архитектуру с очередями.
  Решение сознательно отложено до момента, когда реальная нагрузка это
  потребует.
