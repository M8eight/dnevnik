# ADR 02: Синхронное межсервисное взаимодействие через OpenFeign с graceful degradation

## Статус
Accepted

## Контекст
academic-service хранит только id учеников и получает их данные из
user-service (например, батч-запрос getBatchStudents при сборке журнала).
Синхронный вызов между сервисами — точка отказа: недоступен user-service —
падает и academic-service.

## Рассмотренные варианты
- **Асинхронный обмен через брокер (RabbitMQ/Kafka)** — избыточен для
  прямых запрос-ответных сценариев (данные нужны сейчас, для ответа фронту);
  добавляет eventual consistency, dead-letter очереди.
  Запланирован позже для внутренней почты, где сценарий асинхронный
  по своей природе и можно использовать одностороннюю связь.
- **Синхронный HTTP через OpenFeign** — простая модель запрос-ответ, требует
  отдельной стратегии отказоустойчивости.
- **Кэширование батч-ответов (Redis)** — рассмотрено и отклонено: разные
  комбинации id в списке требуют отдельного сервиса и избыточно ради одного запроса.

## Решение
OpenFeign с тремя уровнями защиты:
1. **Resilience4j** (Circuit Breaker + Retry + Bulkhead (sync, semaphore)) на Feign-клиентах —
   ограничивает каскадные отказы и нагрузку на нестабильный сервис.
2. **Fallback Factory** — при недоступности user-service возвращается список
   с заполненным id в notFound поле и null в поле found вместо падения.
3. **Флаг isDegraded** в ответе — фронт показывает понятную деградацию
   (заглушку) вместо пустых полей.

## Последствия
+ Простая предсказуемая модель запрос-ответ, без брокера и eventual
  consistency.
+ Явный сигнал деградации на фронт (isDegraded) вместо непредсказуемо пустых
  данных.
+ Resilience4j снижает риск каскадных отказов и лишней нагрузки на
  user-service.
− Без кэша каждый батч-запрос идёт напрямую в user-service; при деградации
  доступны только id.
− Синхронная связь остаётся точкой отказа — без очереди/кэша полностью не
  устранить, риск принят осознанно.
− Переход на событийную модель для этого сценария отложен до
  notification-service.
