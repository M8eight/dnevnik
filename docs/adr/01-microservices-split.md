# ADR 01: Микросервисная архитектура и декомпозиция на user-service / academic-service

## Статус
Accepted

## Контекст
Проект не требует микросервисов по нагрузке — модульный монолит закрыл бы
задачу дешевле и был бы проще в реализации (единый деплой, одна БД, без сети между модулями). Но основная цель проекта учебная - практика с со spring cloud, eureka + gateway, resilience logging, поэтому решение принято не из нагрузочных, а из учебных соображений.

## Рассмотренные варианты
- **Модульный монолит** — дешевле в эксплуатации, но не даёт практики с
  Eureka/Gateway/Feign/observability — противоречит цели проекта.
- **Сервис на каждую сущность** (schedule-service, grading-service,
  attendance-service...) — максимальное деление, но каждый тянет свой
  деплой/конфиг/миграции; расписание/классы/предметы слишком связаны, чтобы
  разносить их без постоянных межсервисных вызовов.
- **Два сервиса по бизнес-доменам** (люди vs учебный процесс) — управляемое
  число сервисов, границы совпадают с устойчивыми доменами.

## Решение
Два сервиса с собственными БД:
- **user-service** — пользователи, роли, профили, интеграция с Keycloak;
- **academic-service** — весь учебный домен (годы/периоды/классы/предметы/
  расписание/оценки/посещаемость/дз), хранит только id пользователей/классов,
  имена подтягивает через Feign.

## Последствия
+ Практический опыт с Eureka, Gateway, Feign, distributed logging (Loki/
  Alloy/Grafana).
+ Чёткая граница ответственности — identity/Keycloak изолированы в
  user-service.
+ Нет дублирования данных между сервисами (academic хранит только id).
− Синхронные Feign-вызовы между сервисами — точка отказа (закрыто отдельным
  ADR о resilience).
− Архитектурная сложность (Eureka, Gateway, 2 БД, 2 деплоя) избыточна
  относительно реальной нагрузки — осознанная плата ради учебной цели.
− Согласованность между user_db и academic_db — только по id, без
  транзакционной целостности между сервисами.
