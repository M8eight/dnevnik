# ADR 09: Стратегия тестирования — Testcontainers, WireMock, security-тесты с реальной валидацией подписи JWT

## Статус
Accepted

## Контекст
Микросервисам нужны тесты не только на уровне unit (сервисы, контроллеры,
MapStruct-мапперы), но и интеграционные — на границах, где реальное
поведение отличается от изолированной логики: доступ к PostgreSQL (JPA),
межсервисные вызовы (Feign) и проверка JWT (Spring Security Resource
Server, ADR-0003). На каждой из этих границ была развилка между быстрым/
изолированным вариантом теста и более честным, но более тяжёлым.

## Рассмотренные варианты
- **JPA-тесты на H2 in-memory** — отклонён: H2 расходится в диалекте SQL
  с боевым PostgreSQL
- **JPA-тесты на Testcontainers (реальный PostgreSQL)** — выбран: тесты
  идут против той же СУБД, что и в проде, разница диалектов исключена.
- **Feign-тесты через реальный соседний сервис** (например, в docker-
  compose) — отклонён как медленный и хрупкий вариант для интеграционных
  тестов одного сервиса.
- **Feign-тесты через WireMock** — выбран: изолированный, быстрый мок
  HTTP-стороны, не требует поднятия второго сервиса целиком.
- **Security-тесты через `@WithMockUser`/подмену `Authentication`** —
  отклонён: полностью обходит Resource Server и не проверяет реальную
  логику валидации JWT (парсинг, подпись, клеймы, expiry).
- **Security-тесты с реальной валидацией подписи** (локальная RSA-пара +
  переопределённый `JwtDecoder`, "подменяющий" собой Keycloak) — выбран:
  честно прогоняет боевой код валидации JWT, просто без реального
  Keycloak за ним.
- **Полный E2E через весь docker-compose** (Gateway → user-service →
  academic-service → Keycloak вместе) — не сделан; сознательно отложен
  как отдельная задача на будущее.

## Решение
Тестирование организовано по слоям:

- **Unit-тесты** — сервисы, контроллеры, MapStruct-мапперы (отдельно,
  так как маппинг — источник тихих багов при рефакторинге DTO).
- **JPA-интеграционные тесты** — через **Testcontainers** с реальным
  PostgreSQL, а не H2 — исключает расхождение диалектов SQL.
- **Feign-интеграционные тесты** — через **WireMock**, мокающий HTTP-
  ответы соседнего сервиса без необходимости поднимать его целиком.
- **Security-интеграционные тесты** — `JwtDecoder` в тестовом контексте
  переопределяется на `NimbusJwtDecoder.withPublicKey(...)` с локально
  сгенерированной RSA-парой (`JwtTestUtils`); токены подписываются
  `NimbusJwtEncoder` тем же приватным ключом. Это подменяет только
  источник ключа (Keycloak → локальный тестовый), а сама проверка
  подписи, `issuer`, `expiresAt` и клеймов (`realm_access.roles`,
  `user_id`) проходит через настоящий Spring Security Resource Server —
  включая тестирование `expiredToken()` для проверки обработки
  просроченных токенов.

Полный end-to-end тест через весь стек контейнеров не реализован.

## Последствия
+ Тесты на каждой границе (БД, межсервисный вызов, авторизация) идут
  против реалистичного поведения, а не упрощённой имитации — меньше
  риска, что тест зелёный, а в проде код падает.
+ Security-тесты покрывают реальную логику Resource Server (подпись,
  issuer, expiry, роли), а не просто "пропускают" запрос замоканной
  аутентификацией — ловят регрессии в самой security-конфигурации.
+ Independent от внешних сервисов при прогоне (Testcontainers/WireMock/
  локальный JWK) — тесты воспроизводимы в CI без реального Keycloak/
  соседнего сервиса.
− Testcontainers заметно увеличивает время прогона интеграционных тестов
  относительно H2 (поднятие контейнера PostgreSQL на каждый прогон/класс).
− Нет E2E-покрытия полного пути запроса через Gateway, оба сервиса и
  Keycloak вместе — баги на стыке конфигурации сервисов (роутинг
  Gateway, реальная сеть между контейнерами) не ловятся автоматически,
  остаются на ручной проверке через `docker compose up`.
