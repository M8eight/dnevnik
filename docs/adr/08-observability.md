# ADR 08: Observability через Loki/Alloy/Prometheus/Grafana с трейсингом по traceId в логах

## Статус
Accepted

## Контекст
Микросервисной системе (api-gateway, eureka-server, user-service,
academic-service) нужны логи, метрики и способ проследить путь запроса
через несколько сервисов (Gateway → сервис → Feign → другой сервис →
обратно). Требовалось решение, которое не тянет за собой тяжёлую
инфраструктуру (например, полноценный ELK-стек), и по возможности
использует единую точку визуализации для логов и метрик.

## Рассмотренные варианты
- **ELK (Elasticsearch/Logstash/Kibana)** — отклонён: тяжёлый в
  эксплуатации стек (полнотекстовое индексирование, отдельный кластер),
  избыточный для масштаба проекта.
- **Loki + Grafana Alloy + Prometheus + Grafana** — выбран: Loki
  индексирует только лейблы, а не полный текст логов (в отличие от
  Elasticsearch), что легче в ресурсах и настройке; вместе с Prometheus
  и Grafana образует единый, "родной" для Grafana стек — логи и метрики
  видны в одном инструменте.
- **Push логов напрямую в Loki из приложения** (например, HTTP-appender)
  — отклонён в пользу записи в файл + Alloy tail: если Loki или Alloy
  недоступны, логи не теряются, а продолжают копиться на диске и их
  можно посмотреть руками.
- **Полноценный distributed tracing backend (Zipkin/Tempo)** с
  waterfall-визуализацией спанов — не внедрён; вместо этого трейсинг
  реализован через `traceId`/`spanId` в MDC и корреляцию по логам.

## Решение
Каждый сервис пишет логи через общий `logback`-конфиг:
- `CONSOLE` appender для локальной разработки;
- `ASYNC_FILE` appender (`LogstashEncoder`, JSON) в файл на диск с
  ротацией (`TimeBasedRollingPolicy`, 100MB/файл, 7 дней хранения) —
  файл на диске служит буфером на случай недоступности Loki/Alloy;
  запись асинхронная (`neverBlock=true`), чтобы не блокировать поток
  приложения на I/O.

**Grafana Alloy** тейлит файлы логов всех сервисов и пишет в **Loki**
(хранилище логов). **Grafana** визуализирует логи из Loki.

**Метрики**: через Spring Boot Actuator (`health`, `metrics`,
`prometheus`, `circuitbreakers`) каждый сервис отдаёт `/actuator/prometheus`;
**Prometheus** скрейпит эти эндпоинты, **Grafana** строит дашборды поверх
собранных метрик (в т.ч. percentile-гистограммы по `http.server.requests`
и `http.client.requests`, метрики circuit breaker'ов из ADR-0002).

**Трейсинг**: через `micrometer-tracing-bridge-brave` и
`feign-micrometer` каждому запросу присваивается `traceId`/`spanId`,
которые прокидываются в MDC и попадают в каждую строку лога (в т.ч. через
Feign-вызовы между сервисами). Отдельного tracing-бэкенда (Zipkin/Tempo)
нет — путь запроса (вход в Gateway -> сервис -> Feign-вызов другого сервиса
-> выход из Gateway) восстанавливается фильтрацией логов по `traceId`,
для чего в Grafana настроена отдельная панель быстрого поиска по
`traceId`.

## Последствия
+ Логи, метрики и корреляция запросов между сервисами доступны в одном
  инструменте (Grafana), без необходимости держать несколько отдельных
  UI под разные виды observability-данных.
+ Стек легче в эксплуатации и ресурсах, чем ELK — Loki не индексирует
  полный текст логов.
+ Логи не теряются при сбое Loki/Alloy — файл на диске остаётся
  источником правды, который можно прочитать руками.
+ Асинхронная запись в файл не блокирует основной поток приложения.
− Нет полноценного distributed tracing с waterfall-визуализацией спанов
  (Zipkin/Tempo) — восстановление пути запроса через фильтрацию логов по
  `traceId` менее наглядно и требует ручной сборки картины, особенно при
  большом количестве промежуточных вызовов.
− Alloy тейлит файлы с диска, а не получает логи push-ом напрямую — это
  осознанный компромисс ради надёжности (см. Решение), но добавляет
  задержку между записью строки лога и её появлением в Loki/Grafana
  относительно прямого push.
