# ADR 03: Keycloak как провайдер идентификации и авторизации

## Статус
Accepted

## Контекст
Нужна аутентификация/авторизация для трёх ролей (ученик, учитель,
администратор/родитель) с выдачей и проверкой токенов между фронтендом,
Gateway и сервисами. Цель проекта также учебная — получить опыт с
промышленным auth-сервером, а не с самописной схемой аутентификации.

## Рассмотренные варианты
- **Самописная аутентификация** — хранение паролей, ручная генерация/валидация
  JWT, refresh/revoke. Полный контроль, но нужно реализовывать весь жизненный
  цикл токенов самому.
- **Keycloak** — open-source OIDC-провайдер, self-hosted, разворачивается
  прямо в docker-compose проекта без внешней зависимости.
- **Auth0 / Okta / Firebase Auth** — управляемые SaaS-решения, всерьёз не
  рассматривались: платные/облачные, не дают опыта self-hosted развёртывания.

## Решение
Keycloak как централизованный Identity Provider:
- фронтенд аутентифицируется через `keycloak-js` (Authorization Code flow) и
  получает готовый JWT, не касаясь паролей напрямую;
- бэкенд валидирует JWT как Spring Security OAuth2 Resource Server (по JWK
  Keycloak), не генерируя и не парся токены вручную;
- Для манипуляция с пользователями (создание, удаления, изменения данных) 
  используется keycloak admin api, и отдельный клиент в keycloak с client secret
  и спец правами
- только `user-service` обращается к Keycloak Admin REST API (создание
  пользователей, назначение ролей) — `academic-service` и фронтенд об этом
  не знают.

## Последствия
+ Практический опыт с промышленным auth-сервером (realm, roles, clients,
  Admin API, OIDC-flow).
+ Валидация JWT делегирована Spring Security — меньше риска ошибок в
  самописной криптографии.
+ Чёткая инкапсуляция: Admin API доступен только из `user-service`.
− Ещё один инфраструктурный компонент в docker-compose (Keycloak +
  конфигурация realm).
− Профиль пользователя раздвоен между `user_db` и Keycloak, атомарной
  транзакции между ними нет — согласованность держится на ручных
  компенсациях в `UserOrchestrator` (rollback при сбое create/update);
  сама компенсация от сбоя не защищена (ошибка только логируется).
− Полная зависимость от доступности Keycloak — недоступен он, недоступен
  и вход, и управление пользователями.
