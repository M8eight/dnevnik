# ADR 06: pg_trgm вместо Elasticsearch/full-text или tsvector для поиска пользователей

## Статус
Accepted

## Контекст
Админ-панель (/admin/user) нуждается в поиске пользователей с устойчивостью
к опечаткам и поиском по подстроке, а не только по точному совпадению.

## Рассмотренные варианты
- **LIKE '%...%' без индекса** — просто, но full scan, не масштабируется,
  не толерантен к опечаткам.
- **Elasticsearch** — полноценный движок с релевантностью и fuzzy-поиском;
  отклонён — отдельный тяжёлый в эксплуатации кластер, синхронизация
  индекса, несоразмерно для одного поля поиска.
- **Postgres full-text search (tsvector/to_tsquery)** — отклонён: избыточная
  настройка (словари, генерируемые колонки) для точечной задачи; ищет по
  целым лексемам, хуже подходит для ФИО с опечатками, чем триграммы.
- **pg_trgm с GIN-индексом** — поиск по схожести подстрок внутри уже
  существующего PostgreSQL.

## Решение
pg_trgm + GIN-индекс поверх искомых полей. Поиск по триграммам
(подпоследовательности из 3 символов) даёт устойчивость к опечаткам и
частичным совпадениям без выноса поиска во внешнюю систему.

## Последствия
+ Поиск устойчив к опечаткам и подстрокам без дополнительной инфраструктуры.
+ Решение внутри PostgreSQL — не добавляет компонентов в docker-compose, не
  требует синхронизации отдельного индекса.
+ GIN-индекс даёт приемлемую производительность без full scan.
− GIN-индекс увеличивает объём индекса и стоимость записи — для админ-панели
  с редкими изменениями пользователей приемлемо.
