# ADR 04: Database-per-service логически, один физический инстанс PostgreSQL

## Статус
Accepted

## Контекст
При декомпозиции на user-service/academic-service (ADR 01) встал вопрос —
делить ли БД так же, как сервисы. Общая БД сводит на нет изоляцию доменов:
любой сервис может напрямую читать/писать чужие таблицы в обход Feign-
контрактов. Полная реализация паттерна подразумевает и отдельный физический
инстанс PostgreSQL на сервис.

## Рассмотренные варианты
- **Общая БД/схема на оба сервиса** — отклонена: сводит на нет изоляцию
  доменов, создаёт скрытую связанность в обход контрактов.
- **Полное database-per-service** (отдельный инстанс PostgreSQL на сервис) —
  "эталонный" вариант, даёт независимое масштабирование и изоляцию отказа
  на уровне инстанса; отклонён как избыточный для локального pet-проекта
  без реального трафика.
- **Логическое разделение на одном физическом инстансе** — раздельные БД,
  доступ каждого сервиса только к своей, обмен через Feign.

## Решение
Логическое database-per-service: `user_db` и `academic_db` — отдельные базы
на **одном** физическом инстансе PostgreSQL. Каждый сервис работает только
со своей БД через Spring Data JPA, обмен данными — исключительно через
Feign (ADR 02).

## Последствия
+ Логическая изоляция сохранена: ни один сервис не лезет в чужие таблицы
  напрямую.
+ Меньше инфраструктурных расходов локально — не нужно поднимать два
  инстанса PostgreSQL.
− Общий инстанс — единая точка отказа: падение инстанса роняет обе БД
  одновременно, что противоречит идее независимости отказов в
  микросервисах.
− Нет независимого масштабирования БД по нагрузке между сервисами.
